# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A MakeCode Arcade project (PXT target `arcade`, editor 4.1.17) implementing a tiny one- or two-player Robo Rally: each player is dealt a random hand of 6 cards, commits 4 of them to a program, and the robots execute their programs register by register on a tile grid with walls, lava, holes, conveyor belts and a goal.

It is teaching material for Coding Pirates (volunteer coding club, kids aged 9-11). The kids work in the Blocks view; the adults maintain the engine. The season plan (real RFID cards read by a micro:bit, then multiplayer, then a Minecraft port) and the reasoning behind the current design are in `historical-claude-correspondance.md`. Read it before proposing features so they fit the arc.

## Commands

Day-to-day editing happens in the browser at https://arcade.makecode.com (Import -> Import URL -> this repo, or open the project and use its GitHub sync). To work locally:

A local toolchain **is** set up in this checkout (`node_modules/`, `pxt_modules/`, `built/`, `package.json` and the lockfile are all gitignored), so `npx pxt build` works and is the fastest way to prove a change compiles before the kids see it. To recreate it from scratch:

```
npm install -g pxt
pxt target arcade     # once, in repo root; downloads the target into pxt_modules/ (gitignored)
pxt install
pxt build             # = make build
pxt test              # = make test; compiles and runs test.ts
pxt deploy            # = make deploy (default make target); build + copy to a connected device
pxt serve             # local editor + simulator
```

`test.ts` is the only test file (listed under `testFiles` in pxt.json) and is currently empty. It is excluded when the repo is consumed as a MakeCode extension, so there is no finer granularity than "run pxt test".

Releases: creating a GitHub release triggers `.github/workflows/makecode-release.yml`, which runs `pxt build --cloud` for JS plus samd51 / stm32f401 / rpi hardware and uploads the resulting UF2s to the release.

## Architecture

Two hand-written source files with a deliberate split:

- `custom.ts` is the engine, namespace `roboRally`. Per-robot state (sprite, facing, the four facing images, hand, program, dead/out flags, card UI sprites, start tile, controller) lives in a private `Bot` class; `bots[]` holds them and `current` is the robot whose card is executing. Classes are invisible to Blocks, so this costs the kids nothing. Only exported functions carrying a `//% block` annotation appear in the Blocks toolbox (the "Robo Rally" category); everything else is private engine code. Controls are bound per robot through `controller.player1..2`: left/right cycle the hand, A commits the selected card to the next program slot, up pops the last slot, B marks that robot ready. When every robot is ready, `runProgram()` executes register by register, robot by robot, then runs `boardPhase()`. `step()` is the single movement primitive — one tile, used by both `move()` and `push()` — and calls `fireLanded()` after each step, so a `+3` is checked against lava/goal mid-move, stops at walls, and dies off the edge.
- **Exactly two players, and the engine owns game over.** `MAX_PLAYERS = 2`; `addPlayer` has no player argument. The moment `info.player2` is touched, MakeCode's HUD flips to multiplayer mode *permanently* and calls `raiseLifeZero(false)` for every player, so **nobody gets an automatic game over at zero lives any more** — not even player 1. `addRobot` therefore always registers an `onLifeZero` handler. That handler runs inside the HUD *render* pass, so it must never block: it only sets `bot.out`, and `gameEnded()` (called from `runProgram`) is what actually ends the game.
- `main.ts` is the kid-facing program: the drawn robot sprite, `set tilemap to`, deck composition, one `onCardPlayed` hat per card and one `onLand` hat per tile. This is the file the Blocks editor shows. It is regenerated from `main.blocks` whenever a kid edits blocks, so treat it as theirs, not ours.

Constraints that are not obvious from the code:

- **main.ts must stay decompilable to blocks.** MakeCode regenerates `main.blocks` from `main.ts`. If main.ts uses constructs Blocks cannot represent, the kids get stuck in JavaScript view. Anything non-trivial goes into custom.ts behind a `//% block`. Never hand-edit `main.blocks`; to force the blocks view to be rebuilt, delete it and let the editor decompile `main.ts`. In main.ts, image/tile/tilemap literals may only appear where a shadow expects them: `img`...`` behind `screen_image_picker`, `tilemap`...`` behind `tiles_tilemap_editor`, and `assets.tile`...`` or a `sprites.dungeon.*` reference behind `tileset_tile_picker`.
- **Keep the block surface small, and grow it only by primitives.** The live kid-facing API is: addCards, startGame, addPlayer, onCardPlayed, move, turnLeft/turnRight, shoot, push, onLand, onBetweenCards, die, changeLives, win, theRobot, facing, setLook, robotIsOn. The engine owns exactly the things a kid *cannot* build from other blocks — the four verbs (move, turn, push, shoot) and the two moments (landing on a tile, the gap between two cards). Everything else a kid invents is a card name plus a hat: a U-turn is two `turn left`s, a teleport tile is `on lands on` plus the native `place on random tile`, a conveyor is `on ... is on ... between cards` plus `push robot`, a gear is that same hat plus `turn right`. When a new idea does need engine support, add the missing *primitive*, not the feature. Prefer a native MakeCode block over a new custom one whenever the native path is not harder for a kid: `say`, `place on random tile` and `start effect` all work on the robot now that `theRobot` returns the sprite.
- **`onBetweenCards` is the board's turn.** It fires once per register, after every robot has played that register's card, for each living robot standing on the named tile. That is the only hook that exists between two of a kid's own cards; without it a conveyor belt is not expressible at all.
- **Never change a `blockId`.** Every block carries an explicit `blockId=roboRally_*`. The id is what saved `.blocks` files reference, so renaming one silently breaks every kid project; the visible block text can change freely.
- **Card strings are free-form.** Cards are plain strings matched against the `onCardPlayed` hats; nothing enforces a fixed set, so a new card costs one `addCards` block and one hat. Conventions are Danish: `V` = venstre (left), `H` = hoejre (right), `U` = U-vending (U-turn, built from two `turn left` blocks), `S` = skyd (shoot), `P` = prut, `+n` / `-n` = forward/back n tiles. A card with no matching hat makes the robot say "<card> ?", which is how a spelling mistake becomes visible instead of silently doing nothing. **Keep card names to two characters:** `image.font5` is 6 px *wide*, so a three-character label is 18 px on a 16 px card and its first column is clipped.
- **Traps in the runtime that the engine is deliberately working around.** `sayText` leaves a stale `sayEndTime` behind whenever the duration is omitted, so a "permanent" bubble can vanish on the next frame; every bubble therefore gets an explicit long duration and is taken down with `sayText("")`. `sprites.onOverlap` handlers run in a *third* fiber, never synchronously, which is why `shoot()` is a synchronous tile-by-tile ray rather than a native projectile — an async overlap handler would have resolved `active()` to the wrong robot and made the shooter shoot himself. Controller button events queue up to 5 per (button, event) pair while a handler runs, so B presses made during `runProgram` replay afterwards; `runEndedAt` swallows them.
- **Two known limits, both in the runtime, neither worth working around.** A speech bubble is positioned at `owner.top - height - 4` and skipped entirely when that is off-screen, so a robot standing in tile row 0 shows no bubble at all — the executing card's slot turning solid yellow is the reliable indicator, the bubble is the bonus. And controls are bound with `Button.onEvent`, which is last-one-wins per (button, event): a kid who adds a native `on A button pressed` block silently replaces the engine's card-commit handler.
- **The engine takes its own speech bubble down *before* running the card**, not after. A card is allowed to say something of its own (the shipped `P` card does), and clearing after the handler would wipe it — including the `"<card> ?"` warning that makes a misspelt card name visible.
- **Anything that moves the robot has to land it.** `step()` calls `fireLanded()` itself, but a kid moving the robot with a *native* block (the documented way to build a teleport tile) does not. `checkLanded()` runs after every card and every between-cards handler and compares the robot's tile against `Bot.landedCol/landedRow`, so a native teleport onto lava still burns. `fireLanded` is re-entrant — a rule can push the robot, which lands it again — so **one shared budget (`landBudget`, reset to `MAX_TILE_CHAIN` before every card and every board phase) is spent by each landing anywhere in the cascade**, and only the outermost `fireLanded` walks the chain. Capping recursion depth and loop iterations separately is not enough: the two multiply out, and two belts shoving each other would run for weeks rather than hang outright. When the budget runs out the robot says `loop?`, so a belt loop looks like a mistake rather than a freeze.
- **Maps are painted in the tilemap editor.** `tilemap.g.jres` holds the real level (`level1`, 10x7, walls in the packed layer bitmap) and `main.ts` sets it with the native `tiles.setCurrentTilemap(tilemap`level1`)`. Walls come from the editor's wall tool and `step()` reads them through `tiles.tileAtLocationIsWall`. **The level has no border, deliberately:** walking off the edge is a fall, and `step()` asks `offMap()` *before* the wall question, because `tiles.tileAtLocationIsWall` and `TileMap.isObstacle` both answer "yes" for every off-map coordinate. `mapFromText` survives as a `deprecated=true` fallback only, and **it deliberately still references `sprites.dungeon.*` gallery tiles, not `myTiles.*`** — a kid can delete a project tile in the asset editor, and a dangling `myTiles.` reference anywhere in `custom.ts` fails the whole compile and takes the Blocks view down with it.
- **10x7 is the largest level that keeps the camera still.** Camera offsets clamp to `[0, max(area - screen, 0)]`, so a 160x112 map on a 160x120 screen pins the camera at (0,0) and the board is always drawn at the top-left. One row more and the camera starts sliding and `cameraFollowSprite` (which can only ever follow one of the two robots) starts to matter. The card rows live at y 96..118 (player 1) and y 1..23 (player 2). Player 1's rows fall entirely below the board except for its last 16 px; player 2's cover tile row 0 and the top half of row 1. **Keep hazards in rows 2-4** — that band is the only part of the board no card row ever covers. **Keep them out of rows 0 and 6, and off the top half of row 1** — the shipped level puts everything in rows 2..4 for exactly this reason.
- **The level tiles are project tiles, not gallery tiles.** `myTiles.floor/wall/lava/goal/start/hole/conveyor` live in `tilemap.g.jres` as `image/x-mkcd-f4` entries with `tilemapTile: true`, so they show up under **My Tiles** in the tilemap editor and a kid can recolour any of them. They were generated from the `sprites.dungeon` gallery originals (`pxt_modules/device/sprites.dungeon.jres`) so they look the same; `floor` was additionally washed out by remapping its white mortar to tan and its brown shadow to grey, which drops the luminance spread from ~164 to ~67. `main.ts` picks them with `assets.tile`name``.
- **The tile picker only lists project tiles.** `tileset_tile_picker` builds its dropdown from tiles referenced by tilemap assets/blocks in the workspace plus project tiles, never the gallery. This is why the pre-refactor program silently compared against `transparency16` and its lava and goal rules never fired. Gallery graphics live under the editor's **Gallery** tab; **My Tiles** holds only project tiles, which is why it was empty before this change.
- **Card UI is see-through by dimming, not by alpha.** Arcade images have no alpha channel — index 0 is the only transparency. A card is therefore a frame around an empty middle, and `shadeCards()` registers a `game.onShade` handler that runs `screen.mapRect` over each card rectangle with the 16-byte `DIM` lookup table. `onShade` draws at z 80, after the tilemap and ordinary sprites but before the cards at z 90, which is the only point where "the tiles behind a card" still exist to be darkened. The robot sits at z 200 so it and its speech bubble are never covered. Card z is deliberately 90 rather than 100: 100 is `scene.HUD_Z` and a tie there is broken by creation order, not intent. The robot sits at 95 and the shot at 96, above the cards but below the HUD. `shadeCards` dims only the rectangles of cards that actually hold something, because dimming an empty slot punches a dark rectangle into the board.
- `pxt.json` `files` is the authoritative compile list. A new .ts file must be added there or MakeCode ignores it.

## Generated and scaffold files

Do not hand-edit: `main.blocks` and `tilemap.g.*` (editor output), `_history` (MakeCode edit history), `assets/` (compiled simulator build for GitHub Pages; `binary.js` is ~2 MB), and the Jekyll scaffold `index.html`, `_config.yml`, `Gemfile`. `.gitattributes` already marks these as linguist-generated. `assets/js/custom.js` is only honoured if `disableTargetTemplateFiles` is set in pxt.json.
