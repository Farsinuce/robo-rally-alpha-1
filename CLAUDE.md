# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A MakeCode Arcade project (PXT target `arcade`, editor 4.1.17) implementing a tiny Robo Rally for **one to four players, aimed at two**: players join in a lobby, each is dealt 6 cards from their own draw pile, commits 4 of them to a program, and the robots execute their programs register by register on a 16x11 tile grid with walls, lava, holes, conveyor belts, lasers and treasure chests. **Hosted online it has two views** - one for player 1 and one shared by everybody else - so a hand can finally be private. The game ends when the last chest has been opened: whoever opened the most wins, and ties are declared a draw. Robots respawn for ever, so nobody is eliminated and there is no last-robot-standing ending in practice.

It is teaching material for Coding Pirates (volunteer coding club, kids aged 9-11). The kids work in the Blocks view; the adults maintain the engine. The season plan (real RFID cards read by a micro:bit, then multiplayer, then a Minecraft port) and the reasoning behind the current design are in `historical-claude-correspondance.md`. Read it before proposing features so they fit the arc.

## Two branches: the finished game and the one the kids build

The repo ships the same game twice, and the difference is **`main.ts` and the project name, nothing else**.

- **`master`** - the finished game. Every card, every tile rule, all the blocks pre-built. This is the reference: what the kids are working towards, and what the adults demo.
- **`lite`** - the starting point. Two card types (`+1` and `H`), one hazard (lava kills you) and the treasure win condition. That is all. The level still has conveyor belts, lasers and holes painted on it, and in `lite` they do **nothing** - which is the point. The map is the to-do list, and every tile a kid brings to life is one `on ... between cards` hat they wrote themselves. Building the rest of `master` out of `lite` *is* the course.

Import either from the same URL:

```
https://github.com/Farsinuce/robo-rally-alpha-1          <- master, the finished game
https://github.com/Farsinuce/robo-rally-alpha-1#lite     <- lite, the starting point
```

`pxt.github.parseRepoId` pulls the part after `#` out as a tag, and `tagToShaAsync` asks for `refs/tags/<tag>` first and falls back to `refs/heads/<tag>` - so a plain branch name resolves. If a MakeCode version ever stops honouring it, the fallback is to import the repo normally and switch branch in the editor's GitHub pane.

**Keeping them in sync.** `custom.ts`, `tilemap.g.*` and this file must be identical on both branches; only `main.ts` and the `name` in `pxt.json` differ. So an engine change lands on `master` and is merged down:

```
git checkout lite
git merge master
git checkout --ours main.ts pxt.json   # keep lite's program and name
git add main.ts pxt.json && git commit
```

Never fix the engine on `lite` - it will be overwritten. And never let the two `main.ts` files converge: if `lite` grows every block, it has stopped being a starting point.

## Commands

Day-to-day editing happens in the browser at https://arcade.makecode.com (Import -> Import URL -> this repo, or open the project and use its GitHub sync). To work locally:

A local toolchain **is** set up in this checkout (`node_modules/`, `pxt_modules/`, `built/`, `package.json` and the lockfile are all gitignored), so `npx pxt build` works and is the fastest way to prove a change compiles before the kids see it. To recreate it from scratch:

```
npm install -g pxt
pxt target arcade     # once, in repo root; downloads the target into pxt_modules/ (gitignored)
pxt install
pxt build             # = make build
pxt test              # = make test; compiles and runs test.ts
pxt deploy            # = make deploy (default make target); build + copy to a connected device
pxt serve             # local editor + simulator
```

`test.ts` is the only test file (listed under `testFiles` in pxt.json) and is currently empty. It is excluded when the repo is consumed as a MakeCode extension, so there is no finer granularity than "run pxt test".

Two checks matter more than `pxt build`, which only proves the code compiles:

```
node tools/check-blocks.js     # does main.ts still turn into BLOCKS?
```

**`pxt build` always exits 0** - grep its output for `error TS`. And a construct Blocks cannot represent does *not* fail a decompile: it silently becomes a grey `typescript_statement` box the kids can neither read nor edit. `tools/check-blocks.js` is the only thing that catches that; it fails on any grey block. Run it after every change to `main.ts`.

`pxt run` cannot run this game - the CLI uses a bare `pxsim` with none of Arcade's shims, and dies on the first one (`control.runInParallel`). To actually play it headlessly, serve a page that loads `pxt-core/built/pxtsim.js`, `pxt-arcade/built/common-sim.js`, `pxt-arcade/built/sim.js` and `built/debug/binary.js`, give it the DOM skeleton the Arcade sim expects (`#root`, `#wrap.game-player`, `canvas#game-screen`, `#game-buttons-container` with `.button-a`/`.button-b`/`.dpad-*`, `#joystick-container`, `#debug-stats`), then `pxsim.Embed.start()` and post a `{type:"run", code}` message.

Three things about driving it that cost an hour each to find out:

- **Press buttons with `pxsim.board().handleKeyEvent(key, pressed, player - 1)`**, key 1=left 2=up 3=right 4=down 5=A 6=B. Not `setButton`: that one starts with `if (inMultiplayerSession && which > pxsim.Key.Menu) return`, so the moment the board is in a hosted session it silently drops every press for players 2-4 - they are supposed to be remote. Remote presses arrive as `{type:"multiplayer", content:"Button"}` and the board applies them with `handleKeyEvent`, which is why that is the honest way in. (Keyboard keys are bound for players 1 and 2 only, so neither is any use for 3 and 4.)
- **Pretend to be the host** with `pxsim.board().multiplayerState.origin = "server"`, or `getOrigin()` stays undefined and the engine never splits the screens.
- **The client screen never reaches the canvas.** The second-screen extension replaces the post-screen frame handler and posts the *client* image instead, so the only way to see it is to hook `pxsim.Runtime.messagePosted` for `{content:"Image"}` and decode `msg.image`: 8 byte header (`87 04 w w h h 00 00`), then column-major 4bpp, `ceil(h/2)` bytes per column rounded up to 4, two rows per byte, low nibble first. `msg.palette` is 16 RGB triples.

Releases: creating a GitHub release triggers `.github/workflows/makecode-release.yml`, which runs `pxt build --cloud` for JS plus samd51 / stm32f401 / rpi hardware and uploads the resulting UF2s to the release.

## Architecture

Two hand-written source files with a deliberate split:

- `custom.ts` is the engine, namespace `roboRally`. Per-robot state (sprite, facing, the four facing images, hand, own draw pile and discard, program, joined/ready/dead/out flags, chest count, start tile, card row image, controller, `PlayerInfo`) lives in a private `Bot` class. `bots[]` holds every registered robot, `playing[]` the ones that actually joined, `current` the robot whose card is executing and `activeBot` the one being prompted. Classes are invisible to Blocks, so this costs the kids nothing. Only exported functions carrying a `//% block` annotation appear in the Blocks toolbox (the "Robo Rally" category); everything else is private engine code.
- **The round is a state machine in its own fiber.** It walks LOBBY -> PROGRAM -> EXECUTE -> (board) -> deal -> PROGRAM ... Button handlers **only ever set a flag**; nothing long-running happens inside one, and `pauseUntil` is what waits. This is why the engine can block on "player 3 must press A" without deadlocking the controls, and it is why the old `running` / `runEndedAt` mutual-exclusion hack is gone.
- **Every blocking wait in the engine has a deadline.** A wait without one is a bug: one nine-year-old who puts a controller down freezes the table with no way out but a power cycle - the system menu has no reset. `PROGRAM_TIME` (15 s, **per player**, counted down in that player's own banner) fills a straggler's program at random out of the cards left in their hand, flashes `TID UDE` and marks them ready; `TURN_TIMEOUT` (3 s) plays their card; `LOBBY_TIMEOUT` (90 s) starts the game.
- **There is no confirm button, and that makes undo load-bearing.** Committing the fourth card ends your turn by itself; "press B when you are done" is one more thing for a nine-year-old to forget, and forgetting it held up the whole table. But a kid mashing A puts a fourth card down by accident constantly, so **`ready` must not close the editing window**: `windowOpen()` asks only about the deadline, `programming()` adds `!ready`, and `undo()` (up *or* B) works right up until your fifteen seconds run out, un-readying you and putting the cursor back on the card it returned. Never clear `bot.deadline` on auto-commit - `windowShut()` already reads `ready`, so the round moves on regardless, and the deadline is the only thing keeping undo alive.
- **The round must not begin before the kid's `on start` stack has finished.** `startGame` is only the *first* of the setup blocks - `addRobots` and `treasure` run after it - and a kid may well put a splash screen or a pause between them. So `startGame` does **not** fork the loop: it registers a `game.onUpdate` handler that forks it once `SETUP_QUIET` (400 ms) has passed since any setup block last ran (each one stamps `setupAt`). `onUpdate` is scene-scoped, so it does not tick at all while `game.splash` has a scene pushed, which covers a blocking splash of any length. Whatever slips through is caught by the lobby, which re-reads `bots` on every pass and will not auto-start a solo game until it has been open `LOBBY_SETTLE` (2 s). The default deck and `countChests()` both run at the *end* of the lobby for the same reason - injecting the default deck from `startGame` gave a kid who put their `add cards` blocks below it twelve extra cards.
- **A button event queued in one phase is replayed into the next.** `PHASE_GRACE` (300 ms after `phaseAt`) swallows them, so the A press that took your turn cannot commit a card the instant programming opens.
- **Two screens, and which one you get decides when you program.** `arcade-second-screen` renders the scene twice per tick and posts the *second* image to the clients, so player 1 sees one thing and players 2-4 share another. The split is not configurable and never will be - it is always P1 vs. everybody else. The engine reads `getOrigin() == "server"` **every frame** (`splitScreens()`), not once, because the same project is built in the editor on one screen and played online on two, and the one-screen layout has to keep working or nobody can see their cards while they are making the thing. That gives three arrangements, and `programPhase` picks one per round:
  - *One screen* (solo, or not hosted): every row on screen at once, everybody picks together. The old behaviour, kept as the editor fallback.
  - *Hosted, two players*: one screen each, simultaneous, hands hidden from each other. This is what the project is aimed at.
  - *Hosted, three or four*: player 1 starts immediately on their own screen; players 2, 3 and 4 take the shared screen **in turn**, fifteen seconds each. This is the one concession to sequential programming, and it exists only because there is no third screen to give them.
  During EXECUTE both screens follow the robot whose turn it is and show every row: the programs are committed and public by then, and watching the same robot is the point.
- **Card rows must be `secondScreen.Renderable`, not `scene.Renderable`.** `_shouldBeDrawn` checks `instanceof secondScreen.Renderable` and falls through to "draw it on both screens" for anything else - so a plain `scene.createRenderable` would paint player 1's hand onto everybody's screen. Create them with `secondScreen.renderOnZIndex(z, mode, handler)`, which is also what constructs the extension's state and installs its dual render pass; constructing the class directly does neither. A solo game therefore never pays for the second render.
- **Do not use `splash`, `ask` or `show long text` anywhere.** The extension's README says so: they push a scene and pause the game, and the dual renderer does not survive it.
- **Up to four players, and the engine owns game over.** `MAX_PLAYERS = 4`, mapping to `controller.player1..4` and `info.player1..4` by index. The moment `info.player2` is touched, MakeCode's HUD flips to multiplayer mode *permanently* and calls `raiseLifeZero(false)` for every player, so **nobody gets an automatic game over at zero lives any more** - not even player 1. There is now deliberately **no `onLifeZero` handler at all**, because nobody is ever eliminated. `win()` still has the raise-a-flag shape - it sets `pendingWinner` rather than calling `game.gameOverPlayerWin`, which never returns to its caller, and `checkEnd()` between cards is what actually ends the game.
- **Two health, infinite respawns, and `info` must never see zero.** `START_HEALTH` is 2, drawn as one heart: full at 2, half at 1, and nothing at all for the moment between dying and coming back. `hit()` is the only place damage happens; when the damage would take a robot to zero or below it calls `kill()`, which goes **straight from whatever was left back to full** without ever writing 0. That is not tidiness: a one-robot project is in `info`'s single-player mode, where reaching zero life calls `game.over` from inside the render pass and ends the game on the robot's first trip into the lava. Death costs you the rest of this round's program and drops you on the **nearest** stair, not the one you started on - dying in the far corner and walking back is nobody's idea of a turn. Opening a chest patches you up to full as well as scoring a point.
- **Getting knocked about costs you choices, and the `?` joker is how.** Being shot earns one joker; being shoved by another robot's card earns one *per tile*, capped at `MAX_JOKERS` = 4. They arrive in the next hand and **replace** cards you would have drawn rather than being added to it: six cards is what the row holds, and being barged around should cost you options, not hand you extras. They are lent by the engine, so `deal` must not push them onto the discard pile - `Bot.injected` counts how many are on the end of the hand and they are dropped instead. A conveyor belt does *not* earn anybody a joker: `charging` is only true while a robot is acting on one of its own cards. `playCard` knows what `"?"` does even if the kid never wrote a hat for it, because the engine hands them out either way.
- **A join lobby, because `connected` is not a seat count.** `controller.playerN.connected` starts false for *everyone*, player 1 included, and only turns true on a join event or a key press - so it cannot be used at startup to ask "is this player real". Instead every kid presses A to take their seat and player 1 presses B to start; robots that never joined are marked `out` and never reach the board. A single robot skips the lobby, and a 90 s timeout starts the game anyway.
- **Execution is A-gated, one robot at a time, on a half-second pulse.** For each register, for each robot in player order: the camera arrives and the banner turns that player's colour, **500 ms**, the robot says what it is about to do, then either that player presses A or **3 s** pass, the card runs *with the bubble still up*, **500 ms**, the bubble comes down, **500 ms**, next robot. The board's own turn gets the same treatment - banner, 500 ms, belts and lasers, 500 ms. Only `activeBot`'s A is read, so mashing A on another controller cannot spend someone else's turn. **A solo player is never asked to press anything** - there is nobody to keep up with, so `runRound` substitutes a plain `READ_PAUSE`. The bubble is now taken down *after* the card rather than before, which means a card that says something of its own overwrites it and that is fine; the one exception is the `"<card> ?"` misspelling warning, which `playCard` reports by returning false so the engine leaves it alone to live out its own 2 s.
- `step()` is still the single movement primitive - one tile, used by `move()` and `push()` - and calls `fireLanded()` after each step, so a `+3` is checked against lava mid-move, stops at walls, and dies off the edge. It now shoves a **chain** of robots (bounded by `MAX_PLAYERS`); the old version passed `shove=false` to the shoved robot, which let two robots end up stacked on one tile. Two rules it is easy to get wrong: only `out` stops a robot being *moved* (a robot that merely lost a life this round has respawned and is a body on the board, so it can still be shoved), and after shoving you must ask **the board** whether the tile is free rather than trust `step`'s return value - `step` also answers false when the shoved robot fell off the edge and died, and in that case the tile *is* free.
- **Setup blocks are order-independent, including `play with N robots`.** `add cards` and `treasure` always were (the default deck and `countChests` both run at the end of the lobby). `addRobots` was not: dropped *above* `start Robo Rally` it saw an empty roster and silently returned, and the kid got a one-robot game with no hint why. It now parks the number in `wantRobots` and `startGame` applies it. Block order is not obvious at nine and must never be the difference between working and silently not.
- **Recolouring player 1 has two catches.** Only do it when there is more than one robot - a solo kid keeps the robot they drew - and re-post `mp.postPresenceIcon(1, ...)` afterwards, because the icon posted at registration is the *original* drawing. The shipped robot is drawn in colour 8, which is player 2's colour, so skipping that gave players 1 and 2 identical avatars on the one screen where you pick your seat.
- **Two robots on one tile break everything downstream.** `botAt` returns only the first of them, so the other becomes unshootable and unpushable. `placeOnStart` therefore checks its own stair for an occupant on every respawn and steps aside to the nearest free tile.
- **The board acts on where everyone stood when the phase began.** `boardPhase` snapshots every robot's tile before running a single between-cards handler. Reading a robot's live tile when its own turn came up gave a robot that had just been shoved onto a belt by *another* robot's belt a second ride in the same phase.
- `main.ts` is the kid-facing program: **one** drawn robot sprite, `set tilemap to`, deck composition, `play with 4 robots`, `treasure is ...`, one `onCardPlayed` hat per card and one `onLand` / `on ... between cards` hat per tile. This is the file the Blocks editor shows. It is regenerated from `main.blocks` whenever a kid edits blocks, so treat it as theirs, not ours.

Constraints that are not obvious from the code:

- **main.ts must stay decompilable to blocks.** MakeCode regenerates `main.blocks` from `main.ts`. If main.ts uses constructs Blocks cannot represent, the kids get stuck in JavaScript view. Anything non-trivial goes into custom.ts behind a `//% block`. Never hand-edit `main.blocks`; to force the blocks view to be rebuilt, delete it and let the editor decompile `main.ts`. In main.ts, image/tile/tilemap literals may only appear where a shadow expects them: `img`...`` behind `screen_image_picker`, `tilemap`...`` behind `tiles_tilemap_editor`, and `assets.tile`...`` or a `sprites.dungeon.*` reference behind `tileset_tile_picker`.
- **Keep the block surface small, and grow it only by primitives.** The live kid-facing API is exactly 21 blocks in four groups: **Setup** (addCards, startGame, addRobots, addPlayer, treasure), **Cards** (onCardPlayed, move, turnLeft, turnRight, shoot, push, randomAction), **Tiles** (onLand, onBetweenCards, takeHits, die, win) and **Robot** (facing, health, setLook, robotIsOn). The kid-facing word for damage is *health* and *hits*, and `takeHits` reads the natural way round - a positive number is damage. `shoot` has an optional `hits` argument behind `expandableArgumentMode="toggle"`, so it is still just "shoot" until somebody wants it to hurt more.
  **There is exactly one way to refer to the robot inside a hat, and that is the draggable `robot` parameter.** `theRobot`, `changeLives`, `mapFromText`, `onLanded`, `say` and `cameraFollowsRobot` were all deleted rather than deprecated: there are no saved kid projects to protect yet, and three different ways to say "the robot" was one too many for a nine-year-old. Verbs act on the robot implicitly (`move 1`); native sprite blocks take the `robot` reporter dragged out of the hat. The engine owns exactly the things a kid *cannot* build from other blocks — the four verbs (move, turn, push, shoot) and the two moments (landing on a tile, the gap between two cards). Everything else a kid invents is a card name plus a hat: a U-turn is two `turn left`s, a teleport tile is `on lands on` plus the native `place on random tile`, a conveyor is `on ... is on ... between cards` plus `push robot`, a gear is that same hat plus `turn right`. When a new idea does need engine support, add the missing *primitive*, not the feature. Prefer a native MakeCode block over a new custom one whenever the native path is not harder for a kid: `say`, `place on random tile` and `start effect` all work on the robot once you drag the hat's `robot` reporter into them.
- **`onBetweenCards` is the board's turn.** It fires once per register, after every robot has played that register's card, for each living robot standing on the named tile. That is the only hook that exists between two of a kid's own cards; without it neither a conveyor belt nor a laser is expressible at all. The shipped level's lasers are exactly this: `on robot is on laser between cards` plus `change robot lives by -1`, no new engine primitive.
- **Never change a `blockId`.** Every block carries an explicit `blockId=roboRally_*`. The id is what saved `.blocks` files reference, so renaming one silently breaks every kid project; the visible block text can change freely.
- **Card strings are free-form.** Cards are plain strings matched against the `onCardPlayed` hats; nothing enforces a fixed set, so a new card costs one `addCards` block and one hat. Conventions are Danish: `V` = venstre (left), `H` = hoejre (right), `U` = U-vending (U-turn, built from two `turn left` blocks), `S` = skyd (shoot), `P` = prut, `+n` / `-n` = forward/back n tiles. A card with no matching hat makes the robot say "<card> ?", which is how a spelling mistake becomes visible instead of silently doing nothing. **Keep card names to two characters:** `image.font5` advances 6 px per character, so a two-character label is exactly the 11 px of ink a 14 px card has room for. A longer one is now *cut* to two rather than printed whole - a row is a single image, so an unclipped label ran straight across the neighbouring card. A clipped name is a visible reason to shorten it; a smeared row is not.
- **Traps in the runtime that the engine is deliberately working around.** `sayText` leaves a stale `sayEndTime` behind whenever the duration is omitted, so a "permanent" bubble can vanish on the next frame; every bubble therefore gets an explicit long duration and is taken down with `sayText("")`. `sprites.onOverlap` handlers run in a *third* fiber, never synchronously, which is why `shoot()` is a synchronous tile-by-tile ray rather than a native projectile — an async overlap handler would have resolved `active()` to the wrong robot and made the shooter shoot himself. Controller button events queue up to 5 per (button, event) pair while a handler runs, which is why nothing long-running may happen inside one: the round runs in its own fiber and the handlers only set flags, so there is no backlog to swallow and the old `runEndedAt` window is gone.
- **Hosted multiplayer is a video stream, and stock it is ONE screen.** `pxt_modules/game/multiplayer.ts` posts the whole 160x120 `screen` framebuffer to every client (`initServer` -> `postImage(screen)`), and each client blits it as its background; `postImage` takes no player argument, and joiners only send controller input back. `arcade-second-screen` is the whole trick: it unregisters that post-screen handler and the sprite-render handler, renders the scene **twice** per tick - once to `screen` with the main camera, once to a second 160x120 image with a second camera - and posts the second one instead. That buys exactly **two** views, always P1 vs. everybody else, and no more; three or four kids still share the second one, which is why programming has to take turns above two players. Hosting itself still needs no engine code: `Scene.init` calls `multiplayer.initServer()` and the role comes from the web app. To host: Share -> "host a multiplayer game", and joiners go to `https://aka.ms/a9` with the six-digit code. On real hardware the whole layer is a C++ no-op and there is only one screen, which is the same case as the editor.
- **Two dependencies, and only two.** `device` and `arcade-second-screen` (pinned to commit `b1a0fef` - the repo has no tags, so there is nothing else to pin to; it pulls `arcade-extension-utils` v0.1.0 with it). The second-screen extension earns its place because it is the only way to give a player a private hand, and it adds no blocks a kid will trip over as long as nobody drags one out of its "Second Screen" category. Do not add more.
- **Do not take the `multiplayer` (`mp`) extension dependency.** It would add 20 blocks to a nine-year-old's toolbox, its `mp.onButtonEvent` writes the same last-one-wins `Button.onEvent` slot the engine uses (so whichever registers last silently wins), and once a kid creates a `MultiplayerState` kind the dependency can never be removed without breaking their `main.ts`. Plain `controller.player1..4` + `info.player1..4` need no dependency at all. The one thing worth having, `mp.postPresenceIcon` (the robot avatar in the join lobby), lives in the `game` package and is already available - as does the `multiplayer::getOrigin` shim the engine redeclares to ask whether it is being hosted.
- **One known limit, and one trap that is now fixed.** A speech bubble is skipped when the owner's top is within 3 px of the top of the *screen* - with a scrolling camera that dead zone follows the viewport, not the board, so the executing card's slot turning solid is the reliable indicator and the bubble is the bonus. The other one is fixed: controls are now bound with `Button.addEventListener`, which is additive, instead of `Button.onEvent`, which is last-one-wins per (button, event) - so a kid who adds a native `on A button pressed` block no longer silently replaces the engine's card handler.
- **The engine takes its own speech bubble down *before* running the card**, not after. A card is allowed to say something of its own (the shipped `P` card does), and clearing after the handler would wipe it — including the `"<card> ?"` warning that makes a misspelt card name visible.
- **Anything that moves the robot has to land it.** `step()` calls `fireLanded()` itself, but a kid moving the robot with a *native* block (the documented way to build a teleport tile) does not. `checkLanded()` runs after every card and every between-cards handler and compares the robot's tile against `Bot.landedCol/landedRow`, so a native teleport onto lava still burns. `fireLanded` is re-entrant — a rule can push the robot, which lands it again — so **one shared budget (`landBudget`, reset to `MAX_TILE_CHAIN` = 16 before every card and every board phase) is spent by each landing anywhere in the cascade**, and the outer loop stops as soon as a nested landing has already happened (the global `landings` counter) - a rule that moves the robot through `push`/`move` goes via `step`, which lands it on the new tile itself, so walking the chain again would run that tile's rules twice. Only a *native* move leaves the counter untouched and still needs another pass. The "am I the outermost call" counter is **per robot** (`Bot.landing`) - a robot shoved by another one has to get its own chain of tile rules, and a module-level counter denied it that. Note the budget is also spent by ordinary movement, because `step` lands the robot on every tile it crosses, so it has to stay comfortably larger than the longest move card. Capping recursion depth and loop iterations separately is not enough: the two multiply out, and two belts shoving each other would run for weeks rather than hang outright. When the budget runs out the robot says `loop?`, so a belt loop looks like a mistake rather than a freeze.
- **font5 has no Danish letters, and the engine draws in font5.** Its 113 glyphs stop at ASCII plus a little Latin Extended - no ae, oe, aa in either case. That is why every engine string is spelled `VAELG`, `gaaet`, `UAFGJORT`, and why `fit()` transliterates a card label before printing it: a card the kids naturally name after a Danish word would otherwise come out as a hole. **Speech bubbles are fine** and need no such care - `sayText` picks its font with `image.getFontForText`, which returns font8, and font8 has all six. So a kid's own `say` block can be as Danish as they like; only card names and the banner cannot.
- **A card name is typed twice, and that is the hardest thing this program asks of a nine-year-old.** Once in `add cards` and once in the `on card played` hat. `checkDeck()` runs at the end of the lobby and flashes the first deck card that has no hat (`KORT? XX`) or whose name is longer than the two characters a card can show (`LANGT: XX`), so a mismatch is visible before the first hand is dealt instead of turning up mid-round as a `"X ?"` bubble nobody can trace. One problem at a time, deliberately: fix it and the next one appears.
- **Never compare against a tile that is not on the map.** `tiles.tileAtLocationEquals` routes through `TileMap.getImageType`, which does a linear memcmp over the tileset and, on a miss, **appends the image to the live tileset** and then answers false forever. That is exactly the failure that made the pre-refactor lava and goal rules silently never fire.
- **Maps are painted in the tilemap editor.** `tilemap.g.jres` holds the real level (`level1`, 16x11, walls in the packed layer bitmap) and `main.ts` sets it with the native `tiles.setCurrentTilemap(tilemap`level1`)`. Walls come from the editor's wall tool and `step()` reads them through `tiles.tileAtLocationIsWall`. **The level has no border, deliberately:** walking off the edge is a fall, and `step()` asks `offMap()` *before* the wall question, because `tiles.tileAtLocationIsWall` and `TileMap.isObstacle` both answer "yes" for every off-map coordinate. Note that a dangling `myTiles.` reference anywhere in `custom.ts` fails the whole compile and takes the Blocks view down with it, so the engine names no project tile: every tile reaches it as an `Image` argument the kid picked.
- **The map is 16x11 and the cameras move, so no board row is safe any more.** Camera offsets clamp to `[0, max(area - screen, 0)]`, so a map has to exceed 160x120 px before it can scroll at all; at 256x176 this one is about 1.6 screenfuls each way, which leaves 96x56 px of scroll. It was 20x14, and that was too big: `getTilesByType` scans row major, so the first two players claim the two **top** corners, and the distance that actually matters went from 17 tiles to 13. Shrink it further before adding anything that makes robots meet less often. `updateCamera` (a `game.onUpdate` handler) drives **both** cameras: during EXECUTE both sit on the robot that is acting; while programming, each screen sits on the robot belonging to whoever owns it (the server on player 1, the client on whoever is choosing). With one screen it falls back to the centroid.
  **There is no "pull the camera onto my robot" button any more, and there must not be one.** A shared camera with four claimants and no arbitration is contention dressed up as a feature; the answer was never a button, it was giving the camera an owner at every moment. `mp.setPlayerIndicatorsVisible` is not an answer either, because its `drawIndicators` has no off-screen test and paints a 17x16 badge over *every* robot on *every* frame.
  The old rule "keep hazards in rows 2-4" is therefore **dead**: which board rows sit under the card strip changes every frame. What replaces it is that the strip is see-through - a card is a frame around a hole over a dimmed board - and the robot (z 95) draws above the cards (z 90), so a robot standing under the strip is still visible. `cameraLift()` biases the view so the active robot sits in the middle of the *clear* band above the strip rather than in the middle of the screen.
- **The level tiles are project tiles, not gallery tiles.** `myTiles.floor/wall/lava/goal/start/hole/conveyorRight/conveyorLeft/conveyorUp/conveyorDown/chest/chestOpen/laser` live in `tilemap.g.jres` as `image/x-mkcd-f4` entries with `tilemapTile: true`, so they show up under **My Tiles** in the tilemap editor and a kid can recolour any of them. They were generated from the `sprites.dungeon` gallery originals (`pxt_modules/device/sprites.dungeon.jres`) so they look the same - `chest`/`chestOpen` are `chestClosed`/`chestOpen`, the vertical belts are rotations of `conveyorRight`, and only `laser` is drawn from scratch, because nothing in the gallery reads as "a beam crosses this square"; `floor` was additionally washed out by remapping its white mortar to tan and its brown shadow to grey, which drops the luminance spread from ~164 to ~67. `main.ts` picks them with `assets.tile`name``.
- **The tile picker only lists project tiles.** `tileset_tile_picker` builds its dropdown from tiles referenced by tilemap assets/blocks in the workspace plus project tiles, never the gallery. This is why the pre-refactor program silently compared against `transparency16` and its lava and goal rules never fired. Gallery graphics live under the editor's **Gallery** tab; **My Tiles** holds only project tiles, which is why it was empty before this change.
- **Card UI is see-through by dimming, not by alpha, and it is one renderable rather than forty sprites.** Arcade images have no alpha channel - index 0 is the only transparency. A card is therefore a frame around an empty middle, and `drawUi` (a single `scene.createRenderable(90, ...)`) runs `screen.mapRect` over each occupied card rectangle with the 16-byte `DIM` table before blitting that player's cached row image. z 90 sits after the tilemap and before the robot at 95, which is the only point where "the tiles behind a card" still exist to be darkened; the shot is at 96 and the native HUD at 100. Only cards that actually hold something are dimmed, because dimming an empty slot punches a dark rectangle into the board.
  **A row is hidden by not drawing it, never by moving it off screen.** `mapRect` clamps rather than no-ops off-image *in the simulator* (only the C++/hardware build has the early-out), so an off-screen card would smear a dimmed line down the edge of the board. That, plus needing to hide an eliminated player's row, is why the cards stopped being sprites.
- **Ten cards per player, one row each, four rows.** `font5` advances 6 px per character and is 5 px tall, so a two-character label is 11 px of ink; a **14 px** card is that plus a 1 px frame and is the width at which `printCenter` lands on x = 1 exactly (13 would put ink on the frame). Four program slots + a gap + six hand cards = 154 px at a 15 px pitch, and rows are 7 px on an 8 px pitch, stacked up from y 112. Card frames are drawn in the player's colour (P1 red 2, P2 blue 8, P3 orange 4, P4 green 7 - the same colours MakeCode's own multiplayer HUD and join lobby use), so a kid finds their row by colour, not by position.
- **The banner is painted onto the board, so its text needs a plate.** There is no background to print against: a yellow chest counter over a yellow conveyor belt is simply not there, and the player badges only read because they draw their own filled boxes. `plate()` puts a black rectangle behind the chest counter and behind the message for exactly the characters they occupy - not the whole top row, which would black out a strip of board for nothing.
- **The native per-player HUD is switched off, and the engine draws its own banner.** In 4-player mode `info` paints four 25x9 corner boxes at z 100 - above the cards - and they land exactly where the card rows go. `info.showLife(false)` cannot hide them (in multiplayer mode the global visibility flags are ignored); the per-player properties `info.playerN.showLife/showScore/showPlayer = false` can, and `onLifeZero` keeps firing. `info` is still the store of truth for lives and score, because the game-over dialog builds its P1..P4 grid from `hasScore()` - which is why every robot gets `setScore(0)` at registration and its chest count thereafter.
- **Only a robot still in the game can win it.** Both endings rank the *alive* list, not everyone who ever played: a robot that ran out of lives three rounds ago does not take the trophy on the strength of the chests it opened before it died. And `retire()` is idempotent and is the only thing that takes a robot off the board - the `onLifeZero` handler cannot do it, because it runs in the render pass and must not block, so it raises `out` and `checkEnd` sweeps for robots that are `out` but not yet `retired`.
- **Winning, and the fact that the runtime has no draw.** Last robot standing calls `game.gameOverPlayerWin(n)`. Treasure is `roboRally.treasure(chest, opened)`: landing on a chest swaps the tile, scores it and decrements `chestsLeft`; at zero the most chests wins, and a tie prints `game.setGameOverMessage(true, "UAFGJORT!")` before `game.gameOver(true)` - there is no built-in tie outcome. `chestsTotal` guards the case where a kid picks the treasure tile but never paints one, which would otherwise end the game before it started. `game.setGameOverScoringType(ScoringType.None)` keeps the high-score machinery out of a four-way scoreboard.
- `pxt.json` `files` is the authoritative compile list. A new .ts file must be added there or MakeCode ignores it.

## Generated and scaffold files

`tilemap.g.jres` / `tilemap.g.ts` are normally editor output. The 16x11 level and its `chest` / `chestOpen` / `conveyorUp` / `conveyorDown` / `laser` tiles were written offline by a generator script instead, because the editor is not available on the command line. The formats it reproduces: a tile is base64 of a **column-major** 4bpp image (`87 04 w w h h 00 00` then `ceil(h/2)` bytes per column); the tilemap blob is base64 of an **ASCII-hex string** of `10, w(2 LE), h(2 LE), w*h tile bytes, then the wall layer as w*h 4bpp nibbles ROW major, low nibble first`. Re-paint the level in the browser rather than by hand if you can; if you cannot, regenerate both files together and prove it with `pxt build` plus `node tools/check-blocks.js`.

Do not hand-edit: `main.blocks` (editor output), `_history` (MakeCode edit history), `assets/` (compiled simulator build for GitHub Pages; `binary.js` is ~2 MB), and the Jekyll scaffold `index.html`, `_config.yml`, `Gemfile`. `.gitattributes` already marks these as linguist-generated. `assets/js/custom.js` is only honoured if `disableTargetTemplateFiles` is set in pxt.json.
